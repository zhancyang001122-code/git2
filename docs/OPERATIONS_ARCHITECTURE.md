# ArchFlow 单人自动运维架构

> 状态：已批准实施；云端健康检查与 Codex 巡检均按每 6 小时运行。  
> 更新日期：2026-08-22

## 1. 本次故障结论

线上静态站、Supabase 项目和 `generate` Edge Function 均可用。最近两次失败都集中在第二路 `image2`，上游返回：

```text
Gemini 生图 API 400: 请求体不是合法的 JSON，或不符合 Gemini generateContent 格式
```

根因是 Gemini 参考图 Part 使用了旧式字段 `inline_data.mime_type`。当前 `generateContent` JSON 格式要求 `inlineData.mimeType`。本地修复已改为规范字段，并增加回归测试，防止以后误改回旧格式。该修复尚未发布。

这类 400 不是云端抖动，重复请求不会自行恢复，还会浪费时间。因此运维系统必须先分类，再决定是否重试。

## 2. 目标与边界

第一阶段按个人项目的现实成本设置：

| 指标 | 目标 |
| --- | --- |
| 可用性 | 月度 99.5% |
| 发现故障 MTTD | 6 小时内 |
| 确定性故障恢复 | 15 分钟内 |
| 代码故障修复建议 | 30 分钟内生成 Issue 或 PR |
| 数据 RPO | 24 小时 |
| 生产变更 | 必须由项目所有者批准 |

自动化可以读取健康状态、日志和脱敏错误；可以执行有限重试、熔断、切换到已审批的备用服务；可以让 Codex 创建分支、运行测试和提交 PR。自动化不得读取或输出真实密钥，不得删除生产数据，不得擅自迁移数据库，不得自动合并或发布 AI 生成的代码。

## 3. 总体架构

```text
用户
  │
  ▼
GitHub Pages / 自定义域名
  │
  ▼
Supabase Auth ── Edge Function ── 生图 API 1
                       │          └─ 生图 API 2
                       ├─ image_generation_tasks
                       └─ Storage / Postgres

每 6 小时云端探测
  ├─ 公开站点 HTML
  ├─ Supabase Auth 健康
  └─ 登录后的 Edge 深度检查（1×1 无敏感图片、纯文本响应）
          │
          ▼
结构化健康报告 + 单一 GitHub Incident Issue
          │
          ├─ 确定性恢复：重试、熔断、已审批降级、回滚
          └─ Codex 诊断：读取脱敏日志 → 分支 → 测试 → PR
                                      │
                                      ▼
                                  人工批准发布
```

云端探测负责 24 小时在线，不依赖个人电脑。Codex 定时任务适合自动排查和准备修复，但本地电脑及 Codex App 未运行时不能作为唯一告警渠道。

## 4. 故障分类与自动动作

| 故障 | 例子 | 自动动作 | 是否需要人工 |
| --- | --- | --- | --- |
| 短暂网络错误 | timeout、408、连接重置 | 指数退避，最多 2 次 | 连续失败才告警 |
| 限流 | 429 | 停止新任务、延迟队列、显示稍后重试 | 检查额度与并发 |
| 上游 5xx | 502/503/504 | 熔断 5 分钟；只在有幂等键时重试 | 持续 15 分钟需处理 |
| 协议/代码错误 | 400 schema、解析失败 | 不重试；关闭故障通道；创建 Issue/修复 PR | 必须审 PR 和发布 |
| 鉴权错误 | 401/403 | 不重试；告警；禁止把密钥写日志 | 必须轮换/修正 Secret |
| 额度/账单 | 402、quota | 降级到已审批供应商或暂停 | 必须确认成本 |
| 数据库/RLS/迁移 | SQL/RLS 失败 | 只读诊断、停止写入 | 禁止自动迁移或删数据 |
| 前端版本故障 | 白屏、核心标记缺失 | 回滚到最近通过合成检查的版本 | 首次启用需审批 |

生图 POST 可能已经被供应商接收，不能因一个模糊的 5xx 就盲目重发，否则会重复扣费并生成重复图片。只有供应商提供幂等键，或明确确认请求尚未进入生成阶段时，才允许自动重试。

## 5. 三层自动修复

### L1：应用内自愈（秒级）

- 对读取、状态查询、上传等幂等操作做有限指数退避；
- 对每个模型供应商维护熔断状态；
- 异步任务保存在数据库，刷新页面后仍能恢复查询；
- 用户看到真实分类信息，而不是统一显示“云端错误”；
- 400、401、402、403 不自动重试。

### L2：平台恢复（分钟级）

- 健康探测连续 2 次失败才报警，避免一次网络抖动制造噪声；
- 同类故障只维护一个 Incident Issue，后续失败追加记录，避免刷屏；
- 静态站发布失败时保留上一成功版本；
- Edge Function 新版本部署后必须完成烟雾检查，否则回滚到上一已知正常版本；
- 供应商切换仅限配置中提前登记、验证并设置预算上限的备用通道。

### L3：Codex 辅助修复（十分钟到小时级）

- 触发条件：Incident Issue、错误率阈值或人工发起；
- 权限：只读生产日志；工作区可写；无生产 Secret 明文；
- 输出：根因证据、最小代码修改、回归测试、风险说明、回滚步骤和 PR；
- 禁止：自动合并、自动部署、执行破坏性 SQL、修改账单或域名。

建议的 Codex 定时任务提示词：

```text
检查 ArchFlow 最新未关闭的 [Ops] Issue 和脱敏运行日志。先分类故障；若能在代码中复现，创建独立工作区和 codex/ops-* 分支，做最小修复，运行 pnpm test 与 pnpm build，并提交 PR。不得读取或输出密钥，不得修改生产数据库，不得合并或部署。若证据不足，只更新诊断结论和下一步，不猜测修复。
```

## 6. 本次上线实现

- `scripts/health-check.mjs`：只读检查公开站点、Supabase Auth，并通过专用监控账号检查 Edge capabilities 与 Gemini 请求协议。输出单行 JSON，失败返回非零退出码。
- `.github/workflows/health-check.yml`：每 6 小时执行健康检查，保存 14 天报告，失败时创建或更新一个 GitHub Issue，恢复后自动关闭该 Issue。
- Gemini payload 修复与防回退测试：已在本地完成。

监控使用权限最小化的专用账号，不复用管理员或日常账号；`ARCHFLOW_MONITOR_PASSWORD` 只放 GitHub Actions Secret。协议检查只发送代码内置的 1×1 无敏感图片并要求纯文本 `OK`，不上传用户文件，也不要求生成业务图片。

## 7. 实施顺序

### 阶段 A：本次修复

1. 审阅字段修复、测试结果与回滚点；
2. 先部署 Edge Function；
3. 用一张无敏感内容的测试图执行一次 `image2` 烟雾测试；
4. 观察 15 分钟 Edge 日志和任务表；
5. 失败则立即回滚上一版本。

### 阶段 B：只读监控

1. 创建最小权限监控账号；
2. 配置 GitHub Variables/Secrets；
3. 启用 `.github/workflows/health-check.yml`；
4. 先手动运行，确认日志无密钥和用户内容；
5. 连续运行 24 小时后再接通知渠道。

### 阶段 C：确定性自愈

1. 增加结构化错误码、provider/slot/traceId 和耗时字段；
2. 增加 provider 熔断器与任务恢复；
3. 对已审批备用供应商做无费用 capabilities 检查；
4. 设计幂等键后再考虑生成请求重试；
5. 增加发布后烟雾检查和一键回滚。

### 阶段 D：Codex 自动修复 PR

1. 连接 GitHub Issue 与只读日志；
2. 创建 Codex 定时任务；
3. 强制分支保护、CI、人工 Review 和生产环境审批；
4. 先试运行两周，只允许产出诊断和 PR；
5. 根据误报率再扩大自动化范围。

## 9. 所有 Codex 项目的统一上线流程

每个项目至少应有以下关卡：

1. **开发完成**：测试、构建、依赖与 Secret 扫描通过；
2. **Preview**：独立预览环境，不连接生产写权限；
3. **上线评审**：架构、数据库迁移、成本、监控、回滚逐项确认；
4. **生产发布**：小步发布，发布后自动烟雾测试；
5. **持续监控**：站点、API、依赖供应商、错误率、延迟、费用；
6. **故障处理**：自动分类，确定性动作自动执行，代码变更走 PR；
7. **备份恢复**：每天备份，至少每季度验证能恢复；
8. **复盘改进**：每次事故补一条检测或回归测试，避免同类问题再次靠人工发现。

理想状态不是“完全无人值守”，而是“机器发现与处理常规故障，你只审批高风险变化”。这才是适合一个人的可持续运维。
