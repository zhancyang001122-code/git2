# ArchFlow 单人自动运维架构

> 状态：已批准实施；由 Codex 单一调度源每 18 小时触发一次生产巡检。
> 更新日期：2026-08-23

## 1. 本次故障结论

本次通过真实 JPEG 做端到端生产测试，确认故障不是单一原因：

```text
image1: 502 Upstream service is temporarily unavailable
image2: 400 service timeout, please try again later
前端回归: ReferenceError（首次请求错误引用尚未创建的 task）
```

已上线的修复包括：参考图统一转为最大 2048 像素的标准 JPEG；服务端按文件魔数校验 MIME；`image1` 遇到 502 时自动切换 `image2`；`image2` 对供应商明确返回的 service timeout、429 和 5xx 最多尝试两次；前端轮询跟随服务端返回的真实槽位。客户端本地超时属于结果不确定状态，不会盲目重发，避免重复扣费。真实生产验收已完成一次 `image1 → image2 → 最终图片` 全链路。

历史上的 Gemini schema 400 来自旧式 `inline_data.mime_type` 字段，已改为规范的 `inlineData.mimeType`。schema 400 不应重试；本次 `service timeout` 虽然也是 400，但错误语义明确为瞬态，因此允许有上限的退避重试。运维系统必须同时判断状态码和受控错误分类。

## 2. 目标与边界

第一阶段按个人项目的现实成本设置：

| 指标 | 目标 |
| --- | --- |
| 可用性 | 月度 99.5% |
| 发现故障 MTTD | 18 小时内 |
| 确定性故障恢复 | 15 分钟内 |
| 代码故障修复建议 | 30 分钟内生成 Issue 或 PR |
| 数据 RPO | 24 小时 |
| 生产变更 | 确定性低风险修复通过 CI 后自动发布；高风险变更仍需所有者批准 |

自动化可以读取健康状态、日志和脱敏错误；可以执行有限重试、熔断、切换到已审批的备用服务；可以让 Codex 创建分支、运行测试、提交 PR，并在确定性问题通过必需检查后自动合并和发布。自动化不得读取或输出真实密钥，不得删除生产数据，不得擅自迁移数据库，不得修改域名或账单。证据不足或涉及数据、账单、域名、权限边界的变更不得自动发布。

## 3. 总体架构

```text
用户
  │
  ▼
GitHub Pages / 自定义域名
  │
  ▼
Supabase Auth ── Edge Function ── 生图 API 1
                       │          └─ 生图 API 2
                       ├─ image_generation_tasks
                       └─ Storage / Postgres

每 18 小时 Codex 自动运维
  └─ 手动触发 GitHub Production Health Check
      ├─ 公开站点 HTML
      ├─ Supabase Auth 健康
      ├─ 登录后的 Edge 协议检查
      └─ 两路中性无人物图片端到端生图 canary（验证最终图片）
          │
          ▼
结构化健康报告 + 单一 GitHub Incident Issue
          │
          ├─ 供应商瞬态故障：记录证据和故障转移状态，不连续复测
          └─ 确定性代码故障：脱敏日志 → 分支 → 测试 → PR → CI → 合并 → 部署 → 一次验收
```

GitHub 健康检查在云端执行，但其 18 小时触发节奏由本地 Codex 自动任务负责；本地电脑及 Codex App 长期未运行时，任务可能延后，因此它不能替代独立的外部可用性告警。

## 4. 故障分类与自动动作

| 故障 | 例子 | 自动动作 | 是否需要人工 |
| --- | --- | --- | --- |
| 短暂网络错误 | timeout、408、连接重置 | 指数退避，最多 2 次 | 连续失败才告警 |
| 限流 | 429 | 停止新任务、延迟队列、显示稍后重试 | 检查额度与并发 |
| 上游 5xx | 502/503/504 | 熔断 5 分钟；只在有幂等键时重试 | 持续 15 分钟需处理 |
| 协议/代码错误 | 400 schema、解析失败 | 不重试；创建 Issue 和最小修复；CI 通过后自动发布并验收一次 | 高风险变更才需人工 |
| 鉴权错误 | 401/403 | 不重试；告警；禁止把密钥写日志 | 必须轮换/修正 Secret |
| 额度/账单 | 402、quota | 降级到已审批供应商或暂停 | 必须确认成本 |
| 数据库/RLS/迁移 | SQL/RLS 失败 | 只读诊断、停止写入 | 禁止自动迁移或删数据 |
| 前端版本故障 | 白屏、核心标记缺失 | 回滚到最近通过合成检查的版本 | 首次启用需审批 |

生图 POST 可能已经被供应商接收，不能因一个模糊的 5xx 就盲目重发，否则会重复扣费并生成重复图片。只有供应商提供幂等键，或明确确认请求尚未进入生成阶段时，才允许自动重试。

## 5. 三层自动修复

### L1：应用内自愈（秒级）

- 对读取、状态查询、上传等幂等操作做有限指数退避；
- 对每个模型供应商维护熔断状态；
- 异步任务保存在数据库，刷新页面后仍能恢复查询；
- 用户看到真实分类信息，而不是统一显示“云端错误”；
- 400、401、402、403 不自动重试。

### L2：平台恢复（分钟级）

- 健康探测连续 2 次失败才报警，避免一次网络抖动制造噪声；
- 同类故障只维护一个 Incident Issue，后续失败追加记录，避免刷屏；
- 静态站发布失败时保留上一成功版本；
- Edge Function 新版本部署后必须完成烟雾检查，否则回滚到上一已知正常版本；
- 供应商切换仅限配置中提前登记、验证并设置预算上限的备用通道。

### L3：Codex 自动修复（十分钟到小时级）

- 触发条件：Incident Issue、错误率阈值或人工发起；
- 权限：只读生产日志；工作区可写；无生产 Secret 明文；
- 输出：根因证据、最小代码修改、回归测试、风险说明、回滚步骤和 PR；
- 确定性低风险修复：必需检查通过后自动合并，按现有 GitHub Pages / Supabase 流程部署，并只验收一次；
- 外部供应商瞬态故障：只记录，不连续复测，不制造无意义代码改动；
- 禁止：执行破坏性 SQL、删除或迁移生产数据、修改账单或域名、在证据不足时猜测发布。

建议的 Codex 定时任务提示词：

```text
每 18 小时触发一次 ArchFlow Production Health Check 并读取最新 [Ops] Issue 和脱敏日志。先分类故障；供应商瞬态故障只记录且不连续复测。若能在代码中复现，创建 codex/ops-* 分支做最小修复，运行 pnpm test、pnpm build 与 git diff --check，创建 PR；必需检查通过后自动合并和部署，随后只验收一次。不得读取或输出密钥，不得删除或迁移生产数据，不得修改域名或账单。证据不足时只记录事实和下一步，不猜测修复。
```

## 6. 本次上线实现

- `scripts/health-check.mjs`：检查公开站点、Supabase Auth、Edge capabilities，并通过专用监控账号分别选择两路 API，使用中性内置 PNG 执行真实生图并轮询到最终图片。故障转移会标记为 `degraded`，失败或降级均返回非零退出码。
- Codex `archflow` 自动任务：每 18 小时触发一次 `.github/workflows/health-check.yml`，是唯一的定时调度源。
- `.github/workflows/health-check.yml`：仅保留 `workflow_dispatch`，执行健康检查并保存 14 天报告；失败时创建或更新一个 GitHub Issue，恢复后自动关闭该 Issue。
- Gemini payload 修复与防回退测试：已在本地完成。

监控使用权限最小化的专用账号，不复用管理员或日常账号；`ARCHFLOW_MONITOR_PASSWORD` 只放 GitHub Actions Secret。协议检查和端到端 canary 都使用代码内置的无人物、无文字中性图片，不上传用户文件。端到端 canary 每 18 小时对两路各执行一次，平均约 2.7 次供应商生成调用/天、单个自然日最多 4 次。确认是供应商超时、限流或 5xx 后不进行连续人工复测。

## 7. 实施顺序

### 阶段 A：本次修复

1. 审阅字段修复、测试结果与回滚点；
2. 先部署 Edge Function；
3. 用一张无敏感内容的测试图执行一次 `image2` 烟雾测试；
4. 观察 15 分钟 Edge 日志和任务表；
5. 失败则立即回滚上一版本。

### 阶段 B：只读监控

1. 创建最小权限监控账号；
2. 配置 GitHub Variables/Secrets；
3. 启用 `.github/workflows/health-check.yml`；
4. 先手动运行，确认日志无密钥和用户内容；
5. 连续运行 24 小时后再接通知渠道。

### 阶段 C：确定性自愈

1. 增加结构化错误码、provider/slot/traceId 和耗时字段；
2. 增加 provider 熔断器与任务恢复；
3. 对已审批备用供应商做无费用 capabilities 检查；
4. 设计幂等键后再考虑生成请求重试；
5. 增加发布后烟雾检查和一键回滚。

### 阶段 D：Codex 自动修复与部署

1. 连接 GitHub Issue 与只读日志；
2. 创建 Codex 定时任务；
3. 强制分支保护和 CI，确定性低风险修复通过后自动合并；
4. 使用现有部署流程发布，发布后只做一次针对性验收；
5. 高风险或证据不足的变更停止并请求人工确认。

## 9. 所有 Codex 项目的统一上线流程

每个项目至少应有以下关卡：

1. **开发完成**：测试、构建、依赖与 Secret 扫描通过；
2. **Preview**：独立预览环境，不连接生产写权限；
3. **上线评审**：架构、数据库迁移、成本、监控、回滚逐项确认；
4. **生产发布**：小步发布，发布后自动烟雾测试；
5. **持续监控**：站点、API、依赖供应商、错误率、延迟、费用；
6. **故障处理**：自动分类，确定性动作自动执行，代码变更走 PR；
7. **备份恢复**：每天备份，至少每季度验证能恢复；
8. **复盘改进**：每次事故补一条检测或回归测试，避免同类问题再次靠人工发现。

理想状态不是“完全无人值守”，而是“机器发现与处理常规故障，你只审批高风险变化”。这才是适合一个人的可持续运维。
