# ArchFlow 技术架构与 7 天演示边界

## 先回答三个核心问题

### 1. 只接生图 API 够不够？

不够。ArchFlow 至少需要两类模型能力：

- 语言 / 多模态模型：理解任务书与图片，生成设计方向、空间策略、关键词、比选结论、汇报文案和结构化数据；
- 图像生成 / 图生图模型：完成图纸美化、白模渲染、局部重绘和风格控制。

AI 建模是第三类问题。可靠的 CAD / BIM 建模通常还需要图纸解析、几何规则、格式转换和质量校验服务，不能只靠普通语言模型或生图模型。

### 2. 生成图片和资料是否需要服务器？

面试 POC 可以不需要服务器：模型类型、地址和名称由前端预设，访问者只临时填写语言大模型与生图大模型两把 API Key。但真实产品需要后端，因为它要安全保存服务端密钥、接收大文件、执行长时间任务、记录进度、生成下载文件并控制企业权限。

### 3. 是否必须买一台云服务器？

不一定要先买传统云主机，但需要“云端后端能力”。早期版本可以使用 Serverless API + 对象存储 + 托管数据库，流量和长任务变多后再增加容器或 GPU 任务服务。

## 推荐的真实架构

```text
React / Vite 前端
        │
        ▼
API 网关与身份鉴权
        │
        ├── 语言 / 多模态模型 API
        ├── 图像生成与图生图 API
        ├── CAD / BIM 解析与建模任务
        ├── PPT / PDF 导出服务
        │
        ├── 对象存储：原图、生成图、模型、汇报文件
        └── 数据库：用户、项目、任务状态、资产索引、权限
```

生成任务超过几十秒时，应采用异步任务队列：前端创建任务，后端返回任务 ID，工作服务执行生成，前端轮询或通过 WebSocket / SSE 接收进度，完成后从对象存储读取成果。

## 六个模块对应的技术能力

| 模块 | 核心模型 / 服务 | 7 天演示建议 |
| --- | --- | --- |
| AI 方案灵感 | LLM、多模态理解、案例检索 | 接真实 LLM，案例使用已审核链接 |
| AI 方案设计 | LLM、场地图片理解、结构化 JSON | 接真实 LLM，体量图保留高质量演示样本 |
| AI 图纸美化 | 图生图、边缘 / 线稿约束 | 前端展示真实交互，结果先用样本 |
| AI 建模 | CAD 解析、几何重建、格式转换 | 展示交互原型和技术流程，不承诺生产精度 |
| AI 渲染 | 图生图、深度 / 结构控制 | 已接 `/images/edits` 适配层，单图输出并与上传原图滑杆对比 |
| AI 汇报 | 多模态 LLM、模板引擎、PPT / PDF 导出 | 真实生成文案，版式与下载使用模板 |

## 数据与安全边界

- 浏览器不应长期保存企业 API Key；正式版由服务端持有密钥并按用户计量。
- 上传文件应存入私有对象存储，通过短期签名 URL 访问。
- 数据库只保存元数据与权限关系，不直接塞入大型图片、模型或 PDF。
- 企业项目需要租户隔离、删除策略、访问日志和可配置的数据保留期限。
- 当前 POC 内置 `gpt-5-mini` 与 `gpt-image-2` 两类模型预设，访问者只填写两把 Key；密钥存于当前标签页会话。
- 当前附件只存在对应 React 模块内存，离开模块即释放；真实生成时会临时发送至用户配置的第三方 API。
- 当前“我的资产”是页面内存状态，浏览器刷新或关闭后消失；跨设备与长期留存需要对象存储、数据库和用户身份体系。

## 7 天推荐交付范围

1. 完成 React 前端、六个差异化工作流和资产闭环。
2. 打通方案灵感与方案设计两条真实 LLM 结构化调用，证明接口适配与专业输出能力。
3. 打通“AI 渲染”图生图链路：必须上传参考图、单张输出、原图 / 生成图对比。
4. 用架构图说明对象存储、任务队列、数据库和企业权限如何演进，不在 7 天内硬做完整后端。

## 公开网址的两种含义

- 当前 GitHub Pages 版本：任何人都能打开网址和体验完整 UI；若要发起真实生成，访问者需要填写自己的两把 API Key。
- 正式“打开即生成”版本：访问者无需知道密钥，但必须通过 Serverless / 云端 API 代理调用模型；项目所有者 Key 只存在服务端环境变量，前端永远拿不到。

这比“每个功能都接一个不稳定 API”更适合面试：既展示端到端思考，也能诚实区分已实现能力与下一阶段工程方案。
